# Reflected DOM XSS
 
**Difficulty:** Practitioner  
**Platform:** PortSwigger Web Security Academy  
**Status:** Solved

## 1. Vulnerability Overview

This lab demonstrates a Reflected DOM-based Cross-Site Scripting (XSS) vulnerability.

A reflected DOM XSS occurs when:

1. An application receives attacker-controlled input through an HTTP request.
2. The server processes the input and reflects it in its response.
3. Client-side JavaScript processes the reflected response unsafely.
4. The unsafe processing allows an attacker to execute JavaScript in the victim's browser.

In this lab, the server reflects the search term inside a JSON-like response. The client-side JavaScript then passes that response to `eval()`, which interprets it as JavaScript code.

The vulnerability occurs because attacker-controlled data is processed using an unsafe JavaScript execution function.

## 2. Source & Sink Identification

| Component | Identification |
|---|---|
| Source | `window.location.search` |
| Server-side processing | `search-results` endpoint |
| Reflected data | `searchResultsObj.searchTerm` |
| Dangerous sink | `eval()` |

### Source

```javascript
xhr.open("GET", path + window.location.search);
```

The source is `window.location.search`.

It retrieves the query string from the current URL, allowing user-controlled search input to be included in the HTTP request.

For example:

```text
/?search=hello
```

The query string is appended to the request path and sent to the server.

### Sink

```javascript
eval('var searchResultsObj = ' + this.responseText);
```

The dangerous sink is `eval()`.

It interprets the supplied string as JavaScript code and executes it.

Since the server response contains attacker-controlled data, unsafe input can potentially break out of its intended string context and introduce executable JavaScript.

## 3. Vulnerable Code Analysis

The relevant JavaScript code:

```javascript
function search(path) {
    var xhr = new XMLHttpRequest();

    xhr.onreadystatechange = function() {
        if (this.readyState == 4 && this.status == 200) {
            eval('var searchResultsObj = ' + this.responseText);
            displaySearchResults(searchResultsObj);
        }
    };

    xhr.open("GET", path + window.location.search);
    xhr.send();
}
```

### Step 1: Sending the request

```javascript
xhr.open("GET", path + window.location.search);
xhr.send();
```

The browser sends an HTTP GET request containing the search query.

### Step 2: Receiving the server response

```javascript
this.responseText
```

`responseText` contains the raw response received from the server.

For a normal search such as `hello`, the response was:

```json
{
    "results": [],
    "searchTerm": "hello"
}
```

The server reflects the submitted search term in the `searchTerm` property.

### Step 3: Unsafe evaluation

```javascript
eval('var searchResultsObj = ' + this.responseText);
```

The application concatenates the server response with a JavaScript variable declaration and passes the resulting string to `eval()`.

For a normal response, it effectively evaluates:

```javascript
var searchResultsObj = {
    "results": [],
    "searchTerm": "hello"
};
```

This works normally, but it becomes dangerous when the reflected input can alter the JavaScript syntax.

### Step 4: Displaying search results

```javascript
var searchTerm = searchResultsObj.searchTerm;

var h1 = document.createElement("h1");
h1.innerText = searchResults.length + " search results for '" + searchTerm + "'";
blogHeader.appendChild(h1);
```

The search term is displayed using `innerText`.

`innerText` treats the supplied value as text rather than parsing it as HTML. Therefore, this is not the primary vulnerable sink in this lab.

The main vulnerability occurs earlier, when the server response is passed to `eval()`.

## 4. Network Tab Investigation

The browser's Network tab was essential for understanding this vulnerability.

Initially, inspecting the page source and client-side JavaScript revealed the use of `XMLHttpRequest` and `eval()`. However, it was not immediately clear how the server reflected the search input.

The Network tab helped reveal the complete data flow.

### Step 1: Open the Network tab

1. Open browser Developer Tools.
2. Navigate to the **Network** tab.
3. Enter a normal search term, such as:

```text
hello
```

4. Find the request named `search-results`.

This request is generated by:

```javascript
xhr.open("GET", path + window.location.search);
```

### Step 2: Inspect the server response

Select the `search-results` request and open its **Response** tab.

The response showed:

```json
{
    "results": [],
    "searchTerm": "hello"
}
```

This confirmed that the server was returning the submitted search term inside the `searchTerm` property.

This was an important discovery: the input was not simply being displayed directly by the browser. It was first processed by the server and then reflected in the response.

### Step 3: Test quotation mark handling

Next, a double quote was submitted:

```text
"hello
```

The Network response displayed the reflected value with the quotation mark included.

This test helped investigate whether special characters were being escaped before reaching the client-side code.

### Step 4: Test backslash handling

A backslash was then submitted:

```text
\hello
```

The response showed:

```json
{"results":[],"searchTerm":"\hello"}
```

This suggested that the backslash was not being handled safely in the response.

Next, the following input was tested:

```text
\"hello
```

The raw Network response showed:

```json
{"results":[],"searchTerm":"\\"hello"}
```

This was the critical observation.

The response contained two backslashes before the double quote.

The distinction matters because, in a JavaScript string literal, `\\` represents one literal backslash. The following double quote can then terminate the string.

This indicated that the reflected input could potentially escape the intended string context when the response was interpreted by `eval()`.

**Important:** Use the Network tab's Response view to inspect the actual server response. The Preview tab may display parsed data, which can make escaping characters less obvious.

## 5. Proof of Concept (PoC)

The following payload successfully executed JavaScript:

```javascript
\"-alert(1)}//
```

The payload was submitted through the search functionality.

<details>
<summary>Payload breakdown</summary>

### `\"`

The backslash and double quote manipulate the string boundary.

Because the response contains an escaped backslash, the resulting JavaScript interpretation allows the double quote to terminate the string.

### `-alert(1)`

After escaping the string, the payload introduces a JavaScript expression that calls `alert(1)`.

The minus sign is used as an operator to make the expression syntactically valid in this context.

### `}`

Closes the surrounding JavaScript object.

### `//`

Starts a single-line JavaScript comment.

This comments out the remaining characters on that line, preventing the trailing response content from interfering with the injected expression.

</details>

<details>
<summary>How the payload changes the JavaScript structure</summary>

The original response structure is conceptually:

```javascript
var searchResultsObj = {
    "results": [],
    "searchTerm": "hello"
};
```

The injected input changes the structure so that the reflected value can escape the intended string and introduce an executable expression.

The important point is that the payload does not execute merely because it appears in the response. It executes because the application passes the response to `eval()`.

</details>

**Result:** The `alert(1)` function executed successfully, confirming the DOM XSS vulnerability.

## 6. Attack Flow

1. An attacker crafts a URL containing a malicious search parameter.
2. The victim opens the URL.
3. The browser sends the search request to the server.
4. The server processes the request and reflects the search term in its response.
5. The browser receives the response through `XMLHttpRequest`.
6. The client-side code passes the response to `eval()`.
7. The injected JavaScript is executed in the context of the vulnerable page.

## 7. Potential Impact

Depending on the application's functionality and the victim's privileges, successful XSS exploitation may allow an attacker to:

- Perform actions as the victim within the vulnerable application.
- Access sensitive information available to JavaScript.
- Modify page content or manipulate the user interface.
- Steal accessible session-related information, depending on cookie protections and application design.
- Deliver phishing content through the trusted application origin.

HttpOnly cookies cannot be read directly through `document.cookie`.

## 8. Remediation

### 1. Replace `eval()` with `JSON.parse()`

The application should parse JSON as data instead of executing it as JavaScript.

**Vulnerable:**

```javascript
eval('var searchResultsObj = ' + this.responseText);
```

**Safer:**

```javascript
var searchResultsObj = JSON.parse(this.responseText);
```

`JSON.parse()` parses valid JSON without executing arbitrary JavaScript expressions.

### 2. Validate server-side input

The server should validate incoming search parameters and reject unexpected or invalid input where appropriate.

### 3. Use safe DOM methods

When displaying user-controlled content, prefer safe text-handling methods such as:

```javascript
element.textContent = searchTerm;
```

Avoid inserting untrusted data into HTML or JavaScript execution contexts.

### 4. Implement Content Security Policy (CSP)

A properly configured CSP can provide an additional layer of protection against certain XSS attacks.

However, CSP should not replace fixing the unsafe use of `eval()`.

## 9. Key Learning Points

- Reflected DOM XSS involves both server-side reflection and unsafe client-side processing.
- The source can originate from the URL query string through `window.location.search`.
- The server may reflect user input inside a response rather than directly inside the HTML document.
- `XMLHttpRequest` can retrieve server responses that are subsequently processed by JavaScript.
- `responseText` contains the response received from the server.
- `eval()` is dangerous when its input contains attacker-controlled data.
- JavaScript string escaping and JSON escaping must be handled correctly.
- Network tab inspection is useful for understanding how user input travels from a request into a client-side sink.
- `innerText` was not the vulnerable sink in this particular lab; `eval()` was.

**Final Takeaway:** Do not investigate DOM XSS by looking only at the HTML page. Follow the complete data flow: URL input → HTTP request → server response → JavaScript processing → dangerous sink.
